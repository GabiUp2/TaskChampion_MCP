# LLM Agent Contribution Guidelines

**Purpose:** Rules and requirements for any LLM-based contribution to this project. All AI-assisted development must follow these guidelines to ensure transparency, traceability, and quality.

---

## 1. Authorship Attribution

Every contribution generated or substantially assisted by an LLM **must** be marked with:

| Field | Required | Example |
|---|---|---|
| **Model** | Yes | `claude-sonnet-4-20250514`, `gpt-4o`, `gemini-2.5-pro` |
| **Harness/Interface** | Yes | `Windsurf Cascade`, `Cursor`, `Claude Code CLI`, `ChatGPT`, `API` |
| **Human Reviewer** | Yes | GitHub username of the person who reviewed and approved |

### In code files
Add a comment block at the top of any file substantially generated by an LLM:
```python
# Generated by: Claude claude-sonnet-4-20250514 via Windsurf Cascade
# Reviewed by: gabiup2
# Date: 2026-05-25
```

### In documentation files
Add an attribution line at the bottom of the file or section:
```markdown
---
*Generated by Claude claude-sonnet-4-20250514 via Windsurf Cascade. Reviewed by gabiup2, 2026-05-25.*
```

### In commit messages
Prefix or tag commits that contain LLM-generated content:
```
feat(schemas): add GTD schema preset [LLM: claude-sonnet-4-20250514/Windsurf]
```

## 2. Assumption Logging

**Critical requirement:** If an LLM makes any assertion, claim, or design decision that is **not** directly verified against a source read during the current session, it **must** be logged in `docs/llm_context/assumptions_and_ideas.md` before acting on it.

This includes:
- Claims about API behavior, library capabilities, or tool versions
- Assumptions about user demographics or use cases
- Design decisions based on "best practices" without specific citations
- Inferred behavior from incomplete documentation

Format:
```markdown
### ASM-NNN: <Short description>
- **Date:** YYYY-MM-DD
- **Author:** <model> / <harness>
- **Status:** Unverified
- **Source:** <why you believe this, or "None — assumed based on...">
- **Impact:** <what breaks if this assumption is wrong>
```

## 3. Code Contribution Rules

### Style
- Follow existing code style in the repository (check `.editorconfig`, `pyproject.toml`, or existing files)
- Do not add or remove comments unless the task specifically requires it
- Do not refactor code unrelated to the current task
- Do not introduce new dependencies without documenting the rationale

### Testing
- Every new feature must include or update unit tests
- Every bug fix must include a regression test
- Never delete or weaken existing tests without explicit human instruction
- Test datasets in `tests/fixtures/` should be used for validation

### Security
- Never use `shell=True` in subprocess calls
- Never hardcode secrets, tokens, or API keys
- Validate all external inputs before processing
- Log security-relevant decisions in ADRs

### Documentation
- Update relevant docs when changing behavior
- Cross-reference ADRs for architectural changes
- Keep `ROADMAP.md` current when features are added or changed

## 4. Pull Request Requirements for LLM Contributions

When an LLM-assisted PR is submitted:

1. **PR description** must state which LLM model and harness were used
2. **Each file** substantially generated by LLM must have attribution (see §1)
3. **New assumptions** must be logged in `assumptions_and_ideas.md`
4. **Tests** must pass — the LLM contributor should verify before proposing
5. **Human review** is mandatory — no LLM-generated code merges without human approval

---

## 5. What LLMs Should Read Before Contributing

Before making any changes to this repository, an LLM agent should read (in order):

1. `docs/llm_context/AGENTS.md` — this file
2. `docs/llm_context/assumptions_and_ideas.md` — existing assumptions
3. `docs/adrs/ADRs.md` — architecture decisions
4. `docs/references/Tools_Usage_Reference.md` — upstream tool reference
5. `docs/ROADMAP.md` — current feature plan
6. Relevant schema files in `schemas/` if working on task creation/validation
7. Relevant test fixtures in `tests/fixtures/` if working on tests

---

## 6. Prohibited Actions

LLM agents must **never**:
- Push directly to `main` or `qa` branches
- Delete or weaken tests without explicit human instruction
- Modify the LICENSE or NOTICE files
- Remove attribution from existing LLM-generated content
- Make unlogged assumptions about security-critical behavior
- Introduce dependencies with incompatible licenses
