0. Executive Summary

The API Ingestion Platform is the standardized near-real-time data-ingestion layer between Ternium operational systems and the Microsoft Fabric data platform. It runs on Azure Kubernetes Service (cluster dev-dl-kub-plataforma-bigdata, namespace api-ingestion) and consists of four containerised Python services that share a single output contract (envelope v1.1), one observability spine, and one DataOps drop contract for Bronze-layer landing. This chapter is the single-page handoff: what we built, why we built it this way, and what someone picking this up needs to know in the first 10 minutes.

0.3 Key architecture decisions & trade-offs

The full ADRs (ADR_approach_d, ADR-024, ADR-025) sit in the DXC working repository under API_standard/.archive/approach_d_aks/. The matrix below is the operational distillation — what to remember when you propose a change, and which alternatives were already evaluated.

Decision Alternatives considered Reason chosen Trade-off / what this costs us
AKS pods (Approach D) over Fabric Notebooks / Pipelines / Functions. (A) Fabric Spark notebooks; (B) Fabric Data Pipelines; (C) Azure Functions consumption plan. Need for long-running pull workers, fine-grained observability, and a Python toolchain shared with the rest of Ternium's standard repos. Notebook/pipeline options also bound latency to job startup; Functions complicates Workload Identity to Service Bus + Fabric. Operating an AKS workload is more ops-heavy than a serverless path. Mitigated by the standard pipeline + observability stack (Prometheus / Loki / Tempo / Grafana) shipped here.
Two-server split: pull_api_server + push_api_server. One unified server with a feature flag per direction. Different scaling profiles (polling cadence vs. webhook spikes) and different failure modes (timeout retries vs. dead-lettered validation failures). Separation keeps each module's queue, backpressure and metrics independent. Two images, two pipelines, two ConfigMaps to keep in sync. Shared library services/shared/ contains the non-divergent concerns.
Envelope contract v1.1 with _ingestion + _payload top-level keys. Flat payload with sidecar metadata file; binary protobuf envelope. JSON is queryable in Fabric without a schema registry; verbatim _payload preserves vendor responses for replay / audit; explicit contract_version + service_version let the reader detect producer drift. Larger payload size than a flat structure; producers must always wrap (no "raw passthrough" mode).
Routing-key dispatch: producers tag envelopes with routing_key; a single broker subscriber (Kamil's worker) resolves key → Fabric workspace + lakehouse. Producer-side hard-coded Fabric paths; per-source dedicated topics/subscriptions. Decouples producer code from Fabric topology — new sources ship without redeploying the consumer; topology changes happen in one routing config (ADR-024). One more indirection to debug; mis-typed routing keys silently land in the dead-letter folder until alerted on.
JSONL drop contract for DataOps logging (state / log / job_status_log), not direct Delta writes. Direct Delta upserts from the ingestion pods. Keeps the ingestion side free of Spark/Delta dependencies and write contention; DataOps owns the materialisation (ADR-025). End-to-end latency from "row produced" to "row queryable in the Delta target" is bounded by the DataOps conversion notebook cadence (currently minutes), not seconds.
Dual logging channels: stdout JSON for operators; three independent Fabric handlers for DataOps. Single handler that fans out; OpenTelemetry logs only. Operators and DataOps care about different fields and different latency. Independent handlers also fail independently — a Fabric outage cannot block container stdout. Three queues to size and observe instead of one. Memory pressure on the pod is bounded per handler.
Pre-rendered K8s manifests in repo (no Helm). Helm charts; Kustomize overlays. Matches Ternium's "manifests apply via the ADO pipeline" model. No client-side templating cost; manifests are reviewable as-is in PRs. Cross-env differences (image tag, env vars) are handled by pipeline string substitution; introducing per-env logic requires either a chart re-engineering or pipeline-side complexity.
Workload Identity → AAD for Service Bus, Fabric, and Key Vault. No long-lived secrets in manifests. K8s Secrets sourced from Key Vault; sidecar credential rotators. One auth model end-to-end; nothing to rotate at the pod level; identity reviewable in Azure RBAC. Initial setup requires the platform team to bind the federated identity credential — documented in §0.2 of the runbook (intel checklist item #3).

0.5 Operational states & edge cases

Healthy

/health 200, /ready 200, queue depth below high-water mark, all three Fabric handlers reporting last_write_ok within freshness window.

Degraded — broker reachable, Fabric not

Ingestion continues; Fabric handlers buffer in-memory up to their bounded queue; oldest entries are dropped with a counter increment. Operator alert fires on fabric_handler_dropped_total > 0.

Degraded — broker unreachable

service_bus strategy auto-falls-back to the dead-letter local file path. Operator alert fires; resume requires a one-shot replay job from the dead-letter folder once the broker is back.

Schema drift on a push plugin

Validation rejects the request with 422 + structured error body. Run is logged as quarantined in bronze_job_status_log; no envelope is emitted.

Contract version drift

Envelope contract_version + service_version are written into bronze_ingestion_state. DataOps can gate conversion on version and quarantine unrecognised drops.

Routing key not configured

Kamil's Service Bus consumer logs an unknown-routing-key event and dead-letters the message; the envelope is preserved verbatim for replay once the routing config is updated.

1. Definitions

CronJob

A Kubernetes batch/v1 CronJob that triggers on a schedule (cron expression). Each CronJob is generated from a YAML config file during CI/CD via generate_cronjobs.py. It holds a list of DataPullRequests — one-to-many relationship. When the schedule fires, the CronJob container sends the full list to the Pull API Server via HTTP POST.

configs/cron_jobs/*.yaml → k8s CronJob + ConfigMap

DataPullRequest

A single unit of work describing one external API call to be made. It specifies: the target endpoint, HTTP method, strategy (e.g. http_get), credential acquisition config, pagination rules, timeout, retry policy, and output format. Multiple DataPullRequests can be batched into a single CronJob config.

PullRequestConfig pydantic model in models.py

PullDataProduct

The output artifact produced after a successful data pull. It is a contracted envelope (_ingestion + _payload) carrying tracing/observability metadata alongside the verbatim API response — see §6 Output Envelope & Transport Contract. It is emitted via the configured output strategy (local_file on disk, or service_bus into the in-cluster broker) and logged to the Fabric Lakehouse bronze_job_status_log table for run-level observability.

PushDataEndpoint

A dynamically registered HTTP endpoint on the Push API Server that receives data pushed by external systems (webhooks, event streams). Each endpoint is defined by a YAML plugin config specifying: URL path, accepted content types, body size limits, schema validation (inline YAML or external JSON Schema), and sanitization rules. Endpoints are hot-reloadable without server restart.

configs/push_plugins/*.yaml → PluginInstance

3. Work Distributor for CronJobs

The work distribution layer sits between CronJobs and Pull API Server replicas. Rather than building a custom distributor service, the platform uses the Kubernetes Service (ClusterIP) as its load balancer. This was a deliberate architectural decision to keep the topology simple while maintaining horizontal scalability.

Figure 2 — Work distribution: K8s Service load-balances CronJob requests across Pull API Server replicas.

If the target replica's queue is full, the server returns 503 (backpressure). The CronJob trigger retries with exponential backoff, and the K8s Service may route the retry to a different replica. For future scaling, a dedicated distributor service or message queue (e.g., Azure Service Bus) can replace the K8s Service without changing the CronJob or Pull API Server contracts.

4.2 Flow: Adding a New CronJob

  1. Create a new YAML file in configs/cron_jobs/ (e.g., my_new_api.yaml). Define cron_job.name, cron_job.schedule, cron_job.pull_api_server_url, and a requests list with at least one DataPullRequest.
  2. Commit and push. The CI/CD pipeline runs generate_cronjobs.py --configs-dir ./configs/cron_jobs, which reads the new file and generates a K8s CronJob + ConfigMap manifest.
  3. Apply the generated manifest via kubectl apply -f k8s/cron_jobs/generated/cronjobs.yaml. Kubernetes creates the CronJob resource.
  4. On the next schedule tick, the CronJob spawns a Pod that runs trigger.py, loads the config, generates a root TraceContext, and POST’s the request list to the Pull API Server.
  5. No changes to the Pull API Server are needed — it accepts any valid PullJobRequest regardless of source.

4.3 Flow: Adding a DataPullRequest to an Existing CronJob

  1. Open the existing CronJob config YAML (e.g., configs/cron_jobs/hourly_erp_pull.yaml).
  2. Add a new entry to the requests list with the new source_id, endpoint, strategy, credentials, etc.
  3. Commit and push. CI/CD regenerates the ConfigMap with the updated config and redeploys only the CronJob.
  4. On the next schedule tick, the CronJob sends the expanded request list. The Pull API Server enqueues all items — including the new one — as separate jobs.

4.4 Flow: Removing a DataPullRequest from an Existing CronJob

  1. Open the CronJob config YAML and remove the target entry from the requests list.
  2. Commit and push. CI/CD regenerates and redeploys the CronJob’s ConfigMap.
  3. On the next tick, the CronJob sends the reduced list. The removed request simply stops being sent — the Pull API Server is stateless and does not notice the removal.

4.5 Flow: Removing a CronJob

  1. Delete the YAML file from configs/cron_jobs/.
  2. Commit and push. CI/CD re-runs generate_cronjobs.py; the deleted config produces no manifest.
  3. Apply a kubectl delete cronjob <name> (or let your GitOps tool prune orphaned resources). The K8s CronJob and its ConfigMap are removed.
  4. No other services are affected.

4.6 Flow: Adding a New Pull Strategy

  1. Create a new file in services/pull_api_server/strategies/ (e.g., graphql.py).
  2. Subclass PullStrategy and implement execute() and strategy_name().
  3. Decorate the class with @register_pull_strategy("graphql"). This auto-registers it in the global _PULL_STRATEGY_REGISTRY dict.
  4. Add from . import graphql as _graphql at the bottom of strategies/__init__.py to trigger auto-import on module load.
  5. Rebuild and redeploy the Pull API Server image. CronJob configs can now use strategy: graphql.
# strategies/graphql.py
from . import PullResult, PullStrategy, register_pull_strategy

@register_pull_strategy("graphql")
class GraphQLStrategy(PullStrategy):
    async def execute(self, endpoint, method, headers, query_params,
                      body, credentials, pagination, timeout_seconds, **kwargs):
        # ... GraphQL-specific logic ...
        return PullResult(success=True, data=response_bytes, records_count=n)

    def strategy_name(self) -> str:
        return "graphql"

5.2 Flow: Adding a New Push Data Endpoint

  1. Create a new YAML file in configs/push_plugins/ (e.g., iot_telemetry.yaml). Define plugin_id, name, path (e.g., /ingest/iot), accepted content types, max body size, and validation schema.
  2. If using external JSON Schema, place the .json file in configs/push_plugins/schemas/ and reference it via validation.schema_file.
  3. Update the K8s ConfigMap (push-plugin-configs) to include the new file, and apply.
  4. Trigger a plugin scan by calling POST /admin/scan on the Push API Server (or wait for next restart).
  5. The PluginManager discovers the new file, parses it, computes SHA256 hash, creates a PluginInstance, and registers a dynamic FastAPI route at the configured path.
  6. The endpoint is immediately live and accepting traffic.

5.3 Flow: Hot-Reload via Plugin Module

Figure 9 — Hot-reload mechanism: config hash comparison drives add/update/remove decisions.

5.4 Flow: Removing a Push Data Endpoint

  1. Delete the plugin YAML file from configs/push_plugins/ (or set enabled: false in the config).
  2. Update the K8s ConfigMap and apply.
  3. Call POST /admin/scan. The PluginManager detects the missing/disabled config.
  4. Teardown sequence runs: all registered teardown callbacks execute, then the FastAPI route is removed from app.routes.
  5. The endpoint immediately stops accepting traffic. Existing in-flight requests (if any) complete normally.

5.5 Flow: Adding a New Data-Handling Strategy

The Push API Server uses the Plugin/Observer pattern rather than the Pull server's strategy pattern. To add a new type of data processing, you create a new plugin config YAML that defines the endpoint, validation schema, and output configuration. The server's handler pipeline (validate → sanitize → write) is generic and applies to all plugins.

If you need custom processing logic beyond validate/sanitize/write (e.g., format conversion, enrichment), extend the _handle_push_data function or register plugin-specific teardown/setup callbacks via PluginInstance.register_teardown(). This keeps the core handler clean while allowing plugin-specific extensions.

5.6 Logging Flow

The Push API Server shares the same dual-channel logging architecture as the Pull API Server:

  1. stdout (JSON): All log levels flow through StreamHandler with JsonFormatter + TraceLogFilter. Each log line includes trace_id, span_id, service: "push-api-server".
  2. Fabric Lakehouse: JOB_STATUS (level 25+) records go through FabricLogHandler → thread-safe queue → background thread → async batched JSONL writes to OneLake.
  3. Plugin lifecycle events (registered, updated, removed, error) are logged at INFO level to stdout. Data acceptance/rejection events include the plugin_id and trace_id.

Push-side JOB_STATUS emissions. Each accepted push request emits three JOB_STATUS transitions to the bronze_job_status_log Fabric table, giving DataOps the same visibility into push-ingested data as they have for pull-based jobs:

Figure 8b — Push-side job status lifecycle: each accepted POST emits validating → writing → success transitions to the same bronze_job_status_log table used by pull jobs. DataOps can query both push and pull activity from a single table.

5.7 Tracing Flow

External systems pushing data can optionally include trace headers (X-Trace-Id, X-Span-Id, X-Correlation-Id). If present, the Push API Server extracts them via TraceContext.from_headers(). If no trace headers are present, a new root trace is automatically generated.

The trace context is then:

  1. Set as the current trace via set_current_trace() so all log records in the request scope include trace_id and span_id.
  2. Included in the output envelope written to disk (trace_id + span_id fields), enabling downstream consumers to correlate data lineage.
  3. Passed to any log_job_status() calls for Fabric Lakehouse writes.

6. Output Envelope & Transport Contract

Both the Pull API Server and the Push API Server emit data using the same contracted envelope. The envelope is defined by interface_contract_api_ingestion_dataops.md §3.2 (envelope schema), §3.1 (path layout), and §3.8 (transport strategy). This section is the architecture-side view of that contract — the contract document remains the source of truth.

The contract is enforced in code by a single shared module, shared/envelope.py, which builds the envelope. Servers do not hand-roll envelopes; the contract changes in one place. Both servers then hand the envelope to the OutputManager (in shared/output_strategies/) which selects a transport.

6.2 Raw File Path Convention

When the chosen strategy is local_file, the path follows the contract §3.1 layout exactly. The same layout is reused if/when OneLake is mounted into the pod via a CSI driver — the path that the conversion notebook scans is the same path the pod writes.

7. DataOps Logging JSONL Streams — Drop Contract & Target Schema (v5)

What ingestion ships vs. what DataOps materialises. The ingestion side does not write to tables. It drops append-only JSONL batches into three dedicated OneLake folders (one per stream) via the FabricLakehouseWriter — see logging.fabric.table_path in §8.6 for the path layout. The "three tables" referred to throughout this chapter and the wider contract are the target Delta schemas DataOps materialises on top of those JSONL drops (via the conversion notebook in Artur's DXC-Fabric-dwh-sql-db pipeline). The boundary between the two sides is therefore a file drop with a per-record JSON schema, not a table write. We keep the "table" vocabulary in the rest of this chapter because the JSONL record schema is identical to the target table schema — one row of the table is one line of JSONL — and because DataOps queries the materialised tables, not the raw files.

As of v5, all three JSONL streams are actively populated by the ingestion pods. Each stream has a dedicated Python logging handler (FabricLogHandler, FabricIngestionLogHandler, FabricIngestionStateHandler) that writes JSONL batches to OneLake via its own background thread and FabricLakehouseWriter instance (see §4.7). The schemas below align with the envelope contract v1.1 (§6) — every column that appears in the envelope also appears in at least one stream, so an incident can be triaged end-to-end from a single SQL join after materialisation. The contract document (interface_contract_api_ingestion_dataops.md §3.3 and §3.4) remains the source of truth for the agreed per-record schemas; this section is the architecture-side view plus the v1.1 extensions for tracing and operational fields.

Three streams, three concerns, three handlers. Splitting them avoids both the "one giant table" anti-pattern (cheap to write, painful to evolve) and the "log everything as opaque Parquet" anti-pattern (cheap to log, painful to query). Separate handlers provide failure isolation and independent tuning of batch size and flush intervals on the drop side, and let DataOps tune partitioning & retention independently per target table on the materialisation side.

7.5 DataOps Query Patterns

The schemas are designed around four canonical queries. Each query touches one table primarily and joins the others only when needed — this is what justifies the three-table split.

1. "What is ready to convert?" (cadence-driven, runs every conversion tick)

SELECT source_id, run_id, raw_file_path, trace_id, contract_version
FROM   bronze_ingestion_state
WHERE  status = 'success'
  AND  converted_at IS NULL
  AND  source_id = :source
ORDER  BY started_at;

2. "What failed in the last hour, and where do I look?" (alerting / on-call)

SELECT s.source_id, s.run_id, s.trace_id,
       l.error_message, l.endpoint, l.pod_name,
       l.raw_file_path, l.duration_ms, l.http_status_code
FROM   bronze_ingestion_state s
JOIN   bronze_ingestion_log   l USING (source_id, run_id)
WHERE  s.status = 'failed'
  AND  s.updated_at > now() - interval 1 hour;

3. "Why did this specific run fail?" (trace-driven deep dive)

SELECT timestamp_utc, status, previous_status, duration_ms,
       worker_name, error_message, metadata_json
FROM   bronze_job_status_log
WHERE  trace_id = :trace_id
ORDER  BY timestamp_utc;

4. "What push data arrived recently?" (push-side DataOps visibility)

SELECT source_id, run_id, trace_id, records_processed, bytes_processed,
       timestamp_utc, pod_name, error_message
FROM   bronze_job_status_log
WHERE  metadata_json LIKE '%"engine": "push"%'
  AND  status IN ('success', 'failed')
  AND  timestamp_utc > now() - interval 1 hour
ORDER  BY timestamp_utc DESC;

5. "How is each source trending over time?" (capacity / SLA dashboards)

SELECT source_id,
       DATE(ingested_at)                AS day,
       COUNT(*)                         AS runs,
       SUM(CASE WHEN status='success' THEN 1 ELSE 0 END) AS successes,
       SUM(bytes_written)               AS bytes,
       SUM(records_fetched)             AS records,
       AVG(duration_ms)                 AS avg_duration_ms,
       APPROX_PERCENTILE(duration_ms, 0.95) AS p95_duration_ms
FROM   bronze_ingestion_log
WHERE  ingested_at > now() - interval 30 day
GROUP  BY source_id, DATE(ingested_at);

7.6 Open Questions for DataOps

  1. v1.1 column additions: Add the proposed tracing & transport columns to all three tables (trace_id, span_id, parent_span_id, correlation_id, service_version, contract_version, output_strategy, output_target, routing_key, dead_lettered)? — Recommended: yes, as backfill-defaulted columns.
  2. Single-table vs split: Keep the three-table model, or collapse bronze_ingestion_log + bronze_job_status_log into one wide table with a granularity discriminator? — Recommended: keep the split. The job_status retention is shorter than ingestion_log retention.
  3. Retention: 30/7/7 days (prod/qa/dev) on bronze_job_status_log; indefinite on bronze_ingestion_log & bronze_ingestion_state with monthly compaction. OK?
  4. Partition strategy: Partition on (source_id, DATE(...)). Acceptable cardinality at current source count (~10–30 sources)?
  5. Conversion outcome tracking: Add optional conversion_status column on bronze_ingestion_state (converted / skipped / quarantined), or maintain a separate DataOps-owned bronze_conversion_log table? — Recommended: column on state, matches the existing converted_at pattern.
  6. Idempotency contract: Conversion notebook must be idempotent on (source_id, run_id, page) — envelope already carries content_sha256 for byte-level identity. Confirm DataOps will enforce this on the Delta merge.
  7. Schema evolution: Use Delta's mergeSchema for additive column changes; require explicit migration for renames/drops. OK with both teams?

These questions are tracked alongside the broader contract decisions in interface_contract_api_ingestion_dataops.md §4 (Summary of Decisions Required from DataOps).

9. Testing Strategy

The platform ships with a layered test suite under services/tests/. The intent is that a contributor can verify any non-trivial change end-to-end on a developer workstation without any Azure or Fabric credentials — integration paths that require live cloud resources are explicitly marked and skipped by default. CI re-runs the same suite against a populated environment.

9.1 Test-file layout

Files follow a three-tier naming convention. The prefix tells the reader what scope to expect; the body of the test imports only what's in scope for that tier.

Prefix Scope What it guards
test_unit_* Single module, no I/O, fully synchronous. Pure-function behaviour of building blocks: envelope construction (test_unit_envelope.py), tracing context propagation (test_unit_tracing.py), sanitisation (test_unit_sanitization.py), config loading (test_unit_config_loader.py), credential resolution (test_unit_credentials.py), and the output strategies (test_unit_output_strategies.py).
test_contract_* Cross-module, exercises the wire contract. Schema and on-disk shape of what we emit. test_contract_envelope.py pins envelope v1.1 — field names, required keys, contract_version stamp. test_contract_output.py validates the Files/raw/<source_id>/... path layout and atomic-rename semantics of the local_file strategy.
test_feature_* Component-level integration; in-process FastAPI client. Behaviour of a whole feature loop: test_feature_hot_reload.py (push plugin reload without restart), test_feature_observability.py (metrics + structured logs surface at the right keys), test_feature_sanitization.py (HTML strip + size caps end-to-end), test_feature_watermark.py (last_cursor advance + resume semantics).
test_fabric_handlers.py Fabric-logging integration (skipped without credentials). Exercises the three-handler logging pipeline against the FabricLakehouseWriter. Skipped via the integration marker when FABRIC_AUTH_* environment variables are absent so local pytest runs stay green.
test_config_validation.py Schema regression against the minimal configs in §8.7. Loads every minimal valid config quoted in §8.7 and verifies it round-trips through the Pydantic Settings models. Adding a new required field to a config model without updating §8.7 will fail this test on purpose — it keeps the doc and the code aligned.

9.2 Pytest markers

Two markers are defined in pyproject.toml (see [tool.pytest.ini_options]):

Marker Meaning & how to run
@pytest.mark.integration Test needs a live Azure or Fabric resource (Service Bus broker, OneLake mount, Workload Identity token). CI runs them with creds present; locally, run pytest -m "not integration" to skip.
@pytest.mark.slow Test exercises a long-running path (e.g. backoff escalation across many retries). Default test runs include them; for a fast inner loop use pytest -m "not slow".

9.3 Running the suite

# Install the test extras into the service venv:
cd services
uv sync                                  # or: pip install -r tests/requirements-test.txt

# Full suite, skipping integration (the local default):
pytest -m "not integration"

# Only the contract guards (pinned envelope + on-disk shape):
pytest tests/test_contract_*

# Single feature, with verbose output and stop-on-first-fail:
pytest -xvs tests/test_feature_hot_reload.py

# Full suite WITH integration (CI; requires populated env vars):
pytest
⚠
Local-dev caveat (Catalina, 2026-01-09): unit tests may appear to fail locally if a developer imports something that triggers a DefaultAzureCredential probe at module-import time. The fix is to fence those imports behind the integration marker, not to add real credentials to the local environment. The conftest.py contains the helper fixtures (fake_service_bus, tmp_output_dir, frozen_clock) that let unit tests run hermetically.

9.4 Where this lands in CI

The Ternium standard pipeline (per Catalina's Understanding of standard for the repositories in Ternium, 2026-01-09) runs pre-commit → pytest → docker build → AKS deploy. The pre-commit stage runs Black, Ruff, Pyright, YAML/TOML validation and detect-private-keys (see .pre-commit-config.yaml in the client repo). The pytest stage runs the unit + contract + feature tiers; integration tests are gated on the target environment's credentials being present (dev has them, feature/* branches don't).
